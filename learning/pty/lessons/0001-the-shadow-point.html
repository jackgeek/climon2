Lesson 0001 · PTY session shadowing

Find the shadow point

Your first win: identify the exact boundary where a normal PTY host becomes a shadowable session host.

1. A PTY is a pair, not a screen

On Unix, a pseudoterminal is two connected virtual character devices: a master and a slave. The shell believes the slave is a real terminal. Your host reads and writes the master.

Shell
stdin/stdout/stderr
⇄
PTY slave
terminal behavior
⇄
PTY master
your host

Writing a control character such as Control-C to the master can cause the terminal driver to signal the foreground process group. Reading the master yields what the terminal application wrote through the slave. This is why a PTY is more than two ordinary pipes.1

Key distinction: the kernel supplies one master/slave terminal channel. It does not supply “viewer A,” “viewer B,” permissions, replay, or backpressure policy.

2. Shadowing starts after the master

A session becomes shadowable when the host reads output from the master once and fans those bytes out to multiple clients. Input travels in the opposite direction, but only according to an explicit policy.

Shell
PTY slave
⇄
Session host
owns PTY master
⇄
Owner + shadows
your policy

The session host is the shadow point. It owns the PTY master, reads each output chunk, and decides who receives it. For the first implementation, a shadow is read-only: it receives output but cannot send input.

3. The first Rust shape

Rust ownership maps neatly onto the architecture: one value owns the PTY master and therefore owns the session's platform lifetime.

struct Session {
    // Later: the PTY master handle.
    viewers: Vec<Viewer>,
}

struct Viewer {
    can_write: bool,
}

Vec<Viewer> is a growable list. The field belongs to the Session; when the session is dropped, its fields are dropped too. We will use this ownership rule later to make cleanup explicit rather than accidental.4

4. ConPTY changes the boundary, not the feature

ConPTY does not expose a Unix-style master/slave pair. The Windows host creates separate synchronous input and output channels, creates an HPCON, and starts the child with that pseudoconsole attached.3 ConPTY emits UTF-8 terminal data to the host-facing output channel.2

Your shadowing layer still sits on the host side:

Retrieval practice

Answer before opening each explanation.

Where should output be duplicated for shadows?

After the host reads the PTY master or ConPTY output channel, not by giving each viewer direct ownership of the platform handle.

Does the PTY itself know which viewer is read-only?

No. Viewer permissions and input arbitration belong to the session host.

What is the portable abstraction across Unix and ConPTY?

A session-owned input channel, output channel, resize operation, and lifecycle—not a universal “master file descriptor.”

5. Make the model concrete

Draw three boxes on paper: shell, session host, and viewers. Add one bidirectional arrow between shell and host. Add one output arrow from host to every viewer, but an input arrow only from the owner. If you can explain why the fan-out belongs in the middle box, you have the architecture needed for the first implementation.
