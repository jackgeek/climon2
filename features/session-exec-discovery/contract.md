# Contract: session-exec-discovery

## Purpose
Deliver the first usable climon2 runtime: the launcher starts a command in a real terminal owned by a detached session daemon, immediately connects a controlling client, and discovers live sessions. This feature deliberately ends a session on client disconnect; `session-detach-survival` will amend that temporary exception to the session lifetime described in `CONTEXT.md`.

## Behavior
- **B1.** A manually extracted package contains `<install>/climon2`, `<install>/current`, and `<install>/versions/<v>/{climon2-cli,climon2-daemon,climon2-client}`; executable names have `.exe` on Windows. Adding `<install>` to PATH suffices to invoke it. The launcher reads `current` beside its real executable, independent of the working directory. Its contents are exactly one SemVer 2.0 version, optionally followed by LF or CRLF, with no other whitespace or lines; prerelease and build identifiers are allowed. It launches the CLI in that version directory.
- **B2.** The launcher forwards argument boundaries and values, including empty strings, spaces, quotes, backslashes and Unicode, without shell interpretation; it preserves the environment, working directory and stdin/stdout/stderr handles. On Unix the CLI replaces the launcher with the same PID. On Windows the CLI shares the launcher's console, is contained in a kill-on-close job object, and the launcher ignores Ctrl+C while the CLI can receive it. Closing the launcher terminates its CLI; normal launcher termination returns the CLI's exit status unchanged. The Windows controlling client is also in the launcher's job, but the detached session daemon and the command's separate job are outside it, so closing the launcher disconnects the client without abruptly killing the daemon responsible for B9 cleanup.
- **B3.** Climon2-owned failures exit with code `125` and produce a nonempty stderr diagnostic beginning `climon2: `. Stdout is empty unless `exec` has already relayed command output before the failure; in that case the previously relayed output is permitted, but climon2 adds no failure-related text to stdout. Missing `current`, invalid `current`, and a missing selected version directory have diagnostics containing respectively `current is missing`, `current is invalid`, and `runtime directory is missing`, plus the affected path. Missing/unlaunchable runtime executables name the executable path and include `cannot launch`. Invalid invocation, including bare `climon2`, an unknown subcommand, `exec` without a command, or `list` with unexpected arguments or flags, includes `usage:`. Failed session startup leaves no live command, client or session daemon and no published session record or socket for that attempt. Child status 125 is still passed through, not remapped; the error code distinguishes climon2 errors by convention, not by excluding that child exit status.
- **B4.** The CLI resolves `climon2-daemon` and `climon2-client` only beside its own real executable, including when the CLI is invoked through a symlink where supported. New sessions use that runtime's session daemon and client, regardless of PATH, the working directory or a later edit to `current`. The client launch interface is exactly `climon2-client --protocol 1 attach --metadata <path>`, with `<path>` passed as one argument identifying the session's absolute metadata path.
- **B5.** `climon2 exec <command> [args...]` starts one detached session daemon and runs `<command>` with precisely the arguments after it. Options after `<command>` belong to that command. A bare command is resolved using the inherited PATH; a command containing a path uses the supplied filename, resolved from the invoking working directory when relative, without PATH search. On Windows, a bare name is searched only in inherited PATH directories, in their listed order, with no implicit current-directory-first search. Within each directory, a name with an extension is tried as supplied; a name without an extension is tried with each inherited PATHEXT extension appended in its listed order. No implicit extensions are added beyond PATHEXT. Windows `.exe` and `.com` targets run directly. Windows `.cmd` and `.bat` targets are supported through inherited `%ComSpec%`, using the batch-file invocation and argument escaping of Rust `std::process::Command`; this is the sole implicit-shell exception. Arguments that cannot be passed safely to a batch file, including embedded CR or LF, fail with 125 and a diagnostic beginning `climon2: ` and containing `cannot launch` and the target path, without executing the batch file. Missing or otherwise unlaunchable commands likewise fail with 125 and `cannot launch`, naming the command or resolved path. Apart from this batch-file exception, no shell is added and shell metacharacters are not interpreted. The command inherits the invoking working directory. The daemon is a distinct process, not the CLI or client; on Unix it has no controlling terminal, and on Windows it is detached from the invoking console. It owns a real PTY on Unix or ConPTY on Windows. The command's stdin, stdout and stderr are terminal handles and its controlling terminal can be opened (`/dev/tty` or `CONOUT$`).
- **B6.** On successful `exec`, the same-version client attaches automatically as the first controlling client, with no additional user action. Input reaches the command and command stdout/stderr reach the user's terminal while the command is running, including output before its first read. The command sees the invoking terminal's initial columns and rows on startup; subsequent terminal resizes reach it. Terminal Ctrl+C is delivered to the command with the platform's normal terminal semantics rather than killing only the launcher. On normal exit or a handled climon2 failure the user's terminal modes are restored: on Unix, `stty -g` on the invoking terminal after `exec` matches its value before `exec`; on Windows, a following interactive line in the outer shell echoes its typed characters correctly and executes normally on Enter.
- **B7.** The command receives the invoking environment unchanged except that `CLIMON2_SESSION_ID` becomes its new session GUID, `CLIMON2_SESSION_DEPTH` becomes its decimal session depth, and absent `TERM` becomes `xterm-256color`. An existing `TERM`, including an empty value, is preserved. Each simultaneously running session has a distinct GUID, rendered consistently as lowercase `8-4-4-4-12` hexadecimal digits without braces.
- **B8.** A nonempty inherited `CLIMON2_SESSION_ID` indicates an enclosing session. Without it, depth is 1 regardless of inherited `CLIMON2_SESSION_DEPTH`. With it, depth is the enclosing depth plus 1; an absent or malformed inherited depth is treated as enclosing depth 1. Valid inherited depths are decimal integers from 1 through 4294967295 (digits only, leading zeros allowed). Incrementing the maximum fails with code 125 and a diagnostic containing `session depth overflow`. A successful nested start prints exactly one stderr line `Starting climon2 session nested for the Nth time`, replacing `Nth` with the English ordinal of depth minus 1, including the 11th/12th/13th exceptions. A top-level start prints no nesting notice.
- **B9.** When the command exits, the session ends and `exec` returns its exit code unchanged; on Unix signal termination returns `128 + signal number`. Output already produced by the command is drained to the attached terminal before a normal `exec` exit. For this feature only, disconnecting or killing the controlling client, losing the invoking terminal connection, or forcibly closing the Windows launcher also ends the session. On each end path, the session daemon exits, the command and remaining processes in its terminal process group/job are terminated, and that session's metadata and socket are removed. Other sessions are unaffected. When the controlling client unexpectedly disconnects, including when its process is killed, while the invoking terminal and launcher remain open, `exec` returns 125 with a stderr diagnostic beginning `climon2: ` and containing `client disconnected`. For invoking-terminal loss or forced Windows launcher closure, that exit status and diagnostic are required only if `exec` remains able to report the client loss; process, metadata and socket cleanup is still required.
- **B10.** `exec` requires terminal stdin and stdout; if either is not a terminal it returns 125 with a diagnostic containing `exec requires a terminal`, before starting a session. Stderr may be redirected. `list` and `list --json` require no terminal.
- **B11.** A running session publishes `<climon2 home>/sessions/<guid>.pty`, creating missing state directories. For both `exec` and either listing form, a nonempty `CLIMON2_HOME` selects climon2 home; relative overrides resolve against the invoking working directory. When `CLIMON2_HOME` is unset or empty, climon2 home is `.climon2` beneath the directory named by `HOME` on Unix or `USERPROFILE` on Windows, read from the invoking environment, not from account databases or profile/known-folder APIs. If that required variable is missing or empty, the command fails before creating state or starting a session, with code 125, empty stdout and a stderr diagnostic beginning `climon2: ` and containing `cannot determine home directory: HOME is unset or empty` on Unix or `cannot determine home directory: USERPROFILE is unset or empty` on Windows; there is no fallback. A nonempty `CLIMON2_HOME` does not require either home variable. The record is one UTF-8 JSON object with `format_version` (integer 1), `session_id` (the GUID), `socket_path` (absolute socket path), `daemon_pid` (positive integer PID), `daemon_start_time` (UTC RFC 3339 timestamp of the daemon's process start), `command` (the supplied command string), `args` (array of exact argument strings), `cwd` (absolute command working directory), `depth` (positive integer), `created_at` (UTC RFC 3339 session creation timestamp), and `climon2_version` (the runtime's SemVer string). Timestamps use `Z`, with optional fractional seconds. `daemon_pid` identifies the actual running session daemon, not the CLI, client or command. PID and start time are descriptive, not a substitute for a successful live handshake.
- **B12.** Metadata publication and any replacement are atomic: readers of the final `.pty` path see either no file or a complete valid record, never a partial JSON document. The published file is owned by and accessible only to the session's user: mode 0600 on Unix, a user-SID-only access ACL on Windows. Private permissions apply from first visibility, including to temporary metadata files. Sessions become discoverable only after the socket is listening and the record is complete.
- **B13.** Each daemon listens on AF_UNIX. On Unix its socket is directly within nonempty `$XDG_RUNTIME_DIR`, otherwise `/tmp/climon2-<uid>/`. On Windows it is within `%LOCALAPPDATA%\climon2\run\`, with a basename consisting of lowercase hexadecimal hash characters optionally followed by `.sock`; simultaneous sessions have different paths. Runtime directory paths in metadata are absolute. A missing runtime directory is created user-only; an existing directory must belong to the user and be mode 0700 on Unix or have a user-SID-only access ACL on Windows. The socket is owned by the session's user and has mode 0600 on Unix or a user-SID-only access ACL on Windows. A too-permissive or wrongly owned directory is refused with code 125 and a diagnostic containing `unsafe runtime directory` plus its path; climon2 neither silently repairs it nor falls back elsewhere. Missing Windows LOCALAPPDATA or an unusable/too-long socket path fails with code 125, naming `runtime directory` or `socket path` respectively.
- **B14.** Every accepted socket connection is checked against the daemon user's identity before any session information or terminal data is sent. Unix uses the peer UID; Windows obtains the peer PID using `SIO_AF_UNIX_GETPEERPID` and compares its token user SID. A different user or an unverifiable identity is disconnected without a hello reply and without disturbing an authorized client or the session. A Windows runtime unable to perform this check fails closed with code 125 and a diagnostic containing `peer identity verification unavailable`; directory ACLs alone are never accepted as a substitute.
- **B15.** Protocol 1 frames consist of an unsigned four-byte big-endian payload byte count followed by that many bytes of UTF-8 JSON, with a maximum payload of 1048576 bytes (1 MiB), excluding the prefix. The discovery request is `{"type":"hello","protocol":1}` and its response is `{"type":"hello","protocol":1,"session_id":"<guid>"}`; JSON whitespace and member order are immaterial. The handshake must finish within two seconds of connection acceptance, not two seconds per received fragment. Incomplete handshakes, malformed JSON/UTF-8, zero-length frames, unsupported protocol versions, unknown message types, and lengths above the maximum cause that connection to close without a successful hello, leaving the daemon and established client usable. Fragmented frames are accepted within the deadline; the maximum itself is permitted (for example a hello padded with JSON whitespace). An oversized prefix is rejected without waiting for its payload. A hello-only connection does not gain control, consume the first controlling-client attachment, or end the session when it closes.
- **B16.** `climon2 list` and `climon2 list --json` enumerate session records in climon2 home and include a session only if the socket completes a protocol-1 hello with the same `session_id` as the record and filename GUID. Each discovery connection/handshake attempt has a total two-second deadline; refusal, silence, partial responses, malformed responses, wrong protocol and mismatched IDs are not live. PID existence alone never qualifies a record. Stale records are hidden but left byte-for-byte intact; discovery does not delete their sockets. An otherwise valid record whose `session_id` differs from its filename GUID is silently hidden as stale, without an `ignoring session metadata` warning, even if its socket answers with the record's session ID. A malformed, unreadable or unsupported-format record is skipped with a stderr line beginning `climon2: ignoring session metadata: ` and naming the path. A record that disappears during enumeration is silently skipped. Missing home/sessions directories mean no sessions; other directory-enumeration failures return 125 with a diagnostic naming the path. Successful listing returns 0, including when individual records are ignored, and does not attach a controlling client or disturb one already attached.
- **B17.** With live sessions, `list` writes a plain-text table to stdout with exactly the column headings `SESSION`, `CREATED`, `COMMAND`, `ARGS` in that order and one data line per session. SESSION is the full GUID. CREATED is `created_at` converted to the listing process's local time as `YYYY-MM-DD HH:MM:SS`, using the zone's offset at that record's instant. On Unix, a valid TZ override may select the local zone; on Windows the host's actual OS-configured local zone is used, and TZ-based test control is not assumed. COMMAND is the supplied command. Rows are sorted by descending creation instant, with ascending GUID as the tie-breaker. Alignment spaces are not significant; the output contains no ANSI styling. With no live sessions, stdout is exactly `No climon2 sessions running.` followed by a newline, without a table heading.
- **B18.** Table COMMAND and ARGS cannot inject control characters: backslashes are displayed as `\\`, and Unicode code points U+0000 through U+001F and U+007F through U+009F are displayed as lowercase `\uNNNN` escapes. For ARGS, first apply that escaping to each argument, then surround every argument with POSIX-style single quotes, representing a literal single quote by closing the quotes, emitting backslash-single-quote, and reopening the quotes (`'a'\''b'` for `a'b`). Join arguments with one space; no arguments produces an empty cell and an empty argument displays as `''`. This is a display convention on all platforms, not a promise of pasteable native-shell syntax. If the resulting ARGS cell exceeds 80 Unicode scalar values, show its first 79 followed by the single U+2026 ellipsis character; otherwise show it in full. Other columns are not truncated. No raw control characters originate from record values.
- **B19.** `list --json` writes one JSON array followed by a newline, with one object per live session in the same order as the table, and `[]` for none. Each object contains all the B11 metadata fields with the same types and values, including `depth`, full `args` and full `command`. There is no quoting-for-shell or truncation of these values, no table headings and no non-JSON text on stdout. JSON escapes preserve the original strings on decoding; Unicode code points U+0000 through U+001F and U+007F through U+009F are JSON-escaped, never emitted literally inside strings. Standard short JSON escapes such as `\n` are permitted; other characters in these ranges use `\uNNNN`. Ignored-record warnings remain on stderr.

## Scenarios
- **S1** (B1, B2). Given a complete extracted package in a path containing spaces and Unicode, a foreign working directory and an instrumented CLI, when the launcher is invoked through PATH with empty, spaced, quoted, backslash and Unicode arguments, environment markers and redirected stdio, then that CLI observes exactly the supplied arguments, environment, directory and handles, and its chosen exit code reaches the caller. Repeat with LF, CRLF, no final newline, and prerelease/build SemVer values in `current`.
- **S2** (B1, B3). Given respectively missing `current`, empty/multiline/whitespace/path-traversal/non-SemVer contents, a missing selected version directory and a missing CLI executable, when the launcher runs, then it returns 125, stdout is empty, the corresponding diagnostic fragment and path appear on stderr, and no session processes are started. Given a valid package, when bare `climon2` or `climon2 unknown-subcommand` is invoked, then each returns 125 with empty stdout and a stderr diagnostic beginning `climon2: ` and containing `usage:`, without starting a session.
- **S3** (B2, B6, B9). Given a running launcher and a signal-aware CLI or terminal command, when Unix process identity is inspected or Windows Ctrl+C is sent, then Unix retains the launcher PID through CLI replacement and Windows uses the same console with the launcher surviving Ctrl+C while the intended program receives it. Given a live Windows session, inspection shows its CLI and controlling client in the launcher's job and its daemon and command's job outside that job. When the Windows launcher is forcibly closed while its terminal stays open, then its CLI and client are terminated by the job rather than left running, and the daemon terminates the command/job, removes its metadata and socket, and exits; a separate session remains interactive and discoverable. No exit status or diagnostic is required from a forcibly terminated process.
- **S4** (B3, B4). Given valid companions beside the real CLI and decoy companions on PATH and in the working directory, when `exec` runs, then only the real-directory companions run and the client receives exactly the specified protocol-1 attachment arguments and absolute metadata path. Repeat through a supported CLI symlink and with `current` changed before client launch. Removing either required companion instead produces 125 with `cannot launch` and its path, without using a decoy or leaking a partial session.
- **S5** (B3, B5, B9). Given terminal invocation of `exec` with no command, a nonexistent command or a non-executable command, when startup is attempted, then the appropriate usage or launch diagnostic and code 125 are observed, stdout is empty, and no command, client, daemon, metadata or socket remains. Given `list extra` or `list --unknown`, when invoked, then each returns 125 with empty stdout and a stderr diagnostic beginning `climon2: ` and containing `usage:`. Given Windows PATH directories containing distinct marker programs named `probe.exe` and a decoy `probe.exe` in a working directory absent from PATH, with PATHEXT containing `.EXE`, when `exec probe` runs, then the first PATH directory's program runs, not the working-directory decoy. With only the working-directory decoy available, startup instead fails with 125 and `cannot launch`. With both `probe.exe` and `probe.cmd` in one PATH directory, reversing their order in PATHEXT reverses which marker program runs. Given a command that exits immediately after writing a final marker, then the marker is delivered, its status is returned and the session is cleaned up even if it exits during initial attachment.
- **S6** (B3, B5, B6, B7, B11). Given the generic terminal fixture with empty, spaced, quoted, Unicode and shell-metacharacter arguments, a custom working directory and environment markers, when run by `exec`, then its reports prove exact argv/cwd/environment, terminal stdin/stdout/stderr, an openable controlling terminal, initial size, a new session GUID and matching metadata. Input/output exchanges work before command exit; changing columns and rows changes the fixture's size report. The daemon PID is distinct from command/client/CLI and is detached from the invoking terminal as specified. On Windows, repeat direct launch with a `.com` fixture, and use a PATH-resolved `.cmd` shim with inherited PATHEXT containing `.CMD` and ComSpec identifying `cmd.exe`: `exec shim --resume "argument with spaces" "Unicode-λ"` passes the three argument values to the shim intact, as observed by its argument-reporting output, and metadata retains supplied command `shim` and those arguments. Repeat the shim case with `.bat` and `.BAT`. An argument containing an embedded CR or LF instead yields 125 with `cannot launch` and the batch path on stderr, empty stdout, no batch execution marker and no leaked session state or processes.
- **S7** (B7, B8). Given no inherited session ID, even with an inherited depth, when `exec` starts, then depth is 1 and no nesting notice is printed. Repeat with TERM absent, custom and empty: only the absent case becomes `xterm-256color`, and unrelated environment values remain unchanged.
- **S8** (B7, B8, B11). Given an enclosing session, when it starts an inner `exec`, then the inner GUID differs, its depth increases by 1, metadata and environment agree and exactly one ordinal nesting line appears on stderr. With inherited enclosing depths 1, 2, 3, 10, 11, 12, 20 and 21, the notices use 1st, 2nd, 3rd, 10th, 11th, 12th, 20th and 21st respectively. Missing, zero, negative, nondigit and out-of-range inherited depths yield new depth 2; maximum valid inherited depth instead fails with `session depth overflow` and 125.
- **S9** (B6, B9). Given a connected fixture launched through `exec` from a controlled interactive outer shell, when it exits with 0, 37 or 125 after emitting a final marker, then `exec` returns that status after showing the marker and restores terminal modes. On Unix, termination by SIGTERM yields 143. Also on Unix, given a fixture that has installed a SIGINT trap and reported readiness inside `exec`, when the harness writes the terminal byte `\x03` (rather than signaling a PID), then the fixture's trap emits its interrupt marker and exits 130, and `exec` returns 130, not 125 or `client disconnected`. After each case, on Unix compare `stty -g` captured on the outer terminal before and after `exec`, before any test-driven mode reset: the values match. On Windows, type a fresh marker-producing command line in the outer shell without Enter, observe its characters echo correctly before submission, then send Enter and observe the command's output marker; merely seeing its output after Enter is not an echo check. In each case its daemon disappears, its metadata and socket are removed, and unrelated sessions continue.
- **S10** (B6, B9). Given a live session whose invoking terminal and launcher stay open, when its controlling client process is killed, then `exec` returns 125 with a stderr diagnostic beginning `climon2: ` and containing `client disconnected`. When run from a controlled interactive outer shell, this handled failure also passes S9's before/after `stty -g` check on Unix or subsequent interactive-line echo and execution check on Windows, without a test-driven terminal reset. Given a live session, when instead its invoking terminal is closed, then that status and diagnostic are required only if `exec` remains able to report the client loss. In both cases its command/process group or job and daemon terminate, its metadata and socket disappear, and a separate live session remains interactive and discoverable. Windows console closure must allow daemon cleanup rather than killing the daemon in the launcher's job.
- **S11** (B3, B10). Given piped stdin or redirected stdout, when `exec` is invoked, then it returns 125 with `exec requires a terminal` without starting a session. With terminal stdin/stdout and redirected stderr it succeeds. Both listing forms succeed with all standard streams redirected.
- **S12** (B3, B7, B11, B12). Given two concurrent starts with HOME on Unix or USERPROFILE on Windows set to an isolated temporary directory, when records are observed throughout publication, then each final path is absent or complete JSON with all specified fields and private permissions, GUIDs and socket paths differ, PIDs identify real daemons, and values match the fixture and runtime. Repeat with CLIMON2_HOME unset, empty, absolute and relative: unset/empty uses only `<isolated home>/.climon2`, overrides use their specified location, missing state directories are created, and both listing forms discover those sessions using the same environment. Given CLIMON2_HOME unset or empty and the platform's home variable missing or empty, when terminal `exec`, `list` or `list --json` runs, then it returns 125 with empty stdout and the B11 diagnostic, without creating state or starting a session. Repeat with a nonempty CLIMON2_HOME and missing/empty home variable: execution and discovery succeed in the override directory. No case reads or writes the real user's `.climon2`.
- **S13** (B3, B13). Given a private XDG_RUNTIME_DIR, an unset/empty XDG_RUNTIME_DIR, or Windows LOCALAPPDATA, when a session starts, then the socket is in the specified location, metadata uses its absolute path, and Windows uses a hashed basename. A missing directory is created privately. Positive macOS socket cases use a short private runtime directory as specified under Platforms and shells. A too-permissive/wrong-owner directory is refused with `unsafe runtime directory` and remains unchanged; missing LOCALAPPDATA and an unrepresentable socket path fail with the specified diagnostic and no fallback or leaked session. The too-long socket-path case is a separate negative case, with an otherwise private usable directory, expecting 125 and `socket path`; it must not share an overlong runtime path with positive cases.
- **S14** (B13, B14, B15). Given an authorized live session running as the acceptance gate's single unprivileged user, when that same user sends a valid hello, then it receives the matching session ID and the original controlling client remains usable. Inspection shows the runtime directory and socket belong to that user, with modes 0700 and 0600 respectively on Unix and user-SID-only access ACLs on both on Windows. If Windows peer identity cannot be obtained, startup fails closed with `peer identity verification unavailable` and 125 rather than succeeding with only an ACL check. This scenario requires no connection attempt as another user.
- **S15** (B15). Given a live daemon, when a protocol-1 hello is sent in fragments within two seconds or padded to exactly 1048576 payload bytes, then a matching hello response arrives. Zero-length frames, invalid UTF-8/JSON, protocol 2, an unknown type such as `not-a-climon2-message`, and a length prefix of 1048577 each cause disconnection without successful hello; the oversized case needs no payload. The established client and a subsequent valid probe still work.
- **S16** (B15, B16). Given a connection that sends nothing or slowly drips a partial hello, when two seconds from acceptance elapse, then the daemon has closed it rather than resetting the deadline per fragment. Given a record pointing at a silent, partial-response or mismatched-ID endpoint, when either listing form probes it, then the connection/handshake attempt ends within two seconds and that record is omitted unchanged. Closing a successful hello-only probe never ends the session or takes control.
- **S17** (B11, B16). Given valid live records, a dead socket record, a reused/live unrelated PID, a wrong-session hello, a wrong-protocol hello, malformed/unreadable metadata and an unsupported format_version, when either listing form runs, then only matching live sessions are included, stale files and sockets are not deleted, and ignored invalid records receive the specified stderr warning. Given an otherwise valid record with session_id A saved as `<B>.pty`, where A and B are distinct valid GUIDs and the endpoint replies with A, when either listing form runs, then the record is silently omitted, remains byte-for-byte intact, its socket is not deleted, and no warning names its path. In isolation this mismatched-filename case yields exit 0, empty stderr and the normal empty-list output for the selected form. Missing state directories yield an empty result; a directory-enumeration permission error instead yields 125 and its path. A record disappearing mid-list does not fail the command.
- **S18** (B16, B17). Given several live sessions with different creation instants and two with equal instants, when `list` runs, then it returns 0 and displays the four required headings, full GUIDs, local timestamps and newest-first rows with GUID tie-breaking. Expected timestamps are each record's instant converted to the applicable local zone, not the current instant's offset. On Unix, TZ may be used to control the zone for this check; on Windows, unset TZ in both the listing process and test oracle and use the host's actual OS-configured local zone, without changing system timezone settings. Discovery leaves the controlling clients interactive. With no live sessions it prints exactly the specified no-sessions line.
- **S19** (B17, B18, B19). Given live records whose command/arguments include spaces, empty arguments, single quotes, backslashes, Unicode and characters spanning U+0000 through U+001F and U+007F through U+009F (including NUL, newlines, tabs, ESC, DEL and C1 characters), when listed, then table values obey the escaping and quoting rules without introducing control sequences or extra data rows. Control characters that cannot occur in process arguments may be supplied in synthetic records backed by matching hello endpoints. ARGS lengths of 79, 80 and 81 scalar values after quoting/escaping yield respectively unchanged, unchanged and 79 values plus U+2026. JSON yields untruncated original strings and every metadata field, including depth, in the same order; its raw string contents contain none of the specified control code points literally, and decoding its escapes recovers every original value. The no-session JSON result is `[]` plus newline.
- **S20** (B5, B6, B9, B16). Given each required shell with controlled startup, when started interactively through `exec`, then it executes an input command that emits a distinct marker and is found by both listing forms. On Unix, while the interactive shell is at its prompt, write the terminal byte `\x03`; the shell and `exec` remain running, a later input command emits a second distinct marker, and both listing forms still find that session. Each shell then accepts an explicit shell exit. The reported exit status is propagated, daemon/record/socket cleanup completes, and subsequent listing omits the ended session.

## Platforms and shells
All deliverables and acceptance gates target x64: Ubuntu 24.04 (`bash`, `sh`), macOS (`zsh`, `bash`, `sh`), and Windows Server 2025 (`powershell.exe`, `pwsh.exe`, `cmd.exe`). Each platform runs the generic terminal fixture as well as the per-shell interactive marker/discovery/exit/cleanup scenario. Shell startup files are disabled or isolated using the harness's controlled startup helpers; missing required shells are failures, not substitutions or skips. Unix signal-status cases apply only to Unix; Windows console/job/SID cases apply only to Windows. Filesystem/process/terminal checks must use the native platform, not a Unix substitute for Windows. The harness's 15-second single-wait deadline applies to ordinary progress and cleanup; the explicit two-second protocol deadlines remain stricter. Windows delivery is blocked pending native confirmation of `SIO_AF_UNIX_GETPEERPID`; if unavailable, pause for a contract amendment, never weaken B14.

All positive macOS socket cases, including test-owned fake endpoints, must use a short private runtime directory rather than a deeply nested per-test temporary directory. macOS `sockaddr_un.sun_path` has 104 bytes; allow room for the complete socket basename and terminating NUL in the encoded absolute path. Tests using XDG_RUNTIME_DIR must select a short user-owned mode-0700 directory; tests of the unset/empty fallback use the B13 fallback. Keep space/Unicode install and home paths independent of the short socket directory. Exercise overlong socket paths only in the separate S13 negative case.

S14-S17 require raw AF_UNIX protocol clients and fake AF_UNIX listening endpoints on Windows as well as Unix. Windows CPython does not expose `socket.AF_UNIX`, and the current harness provides no Windows AF_UNIX helper. Acceptance tests must supply a test-local native Winsock helper (for example via ctypes) for connection, listening, framing, deadlines and cleanup; this is test infrastructure, not a product interface. Missing Python socket support does not justify skipping these scenarios or substituting TCP/named pipes. If that helper cannot be supplied within the test-author scope, test delivery is blocked pending a user-approved harness extension.

## Out of scope
Survival after controlling-client disconnect, user-facing attachment to existing sessions, displacement/reclaim, screen restoration, a monitor, install/switch/cleanup commands, automated upgrades, and cross-version compatibility gates. These belong to later roadmap features. Also excluded: fish, zsh on Linux, real Copilot tests, non-x64 platforms, shell emulation, guaranteed pasteable native-shell table arguments, reclamation of stale metadata by `list`, arbitrary bytes that are not valid Unicode in arguments/paths, and cleanup of descendants that deliberately escape the session's process group/job. The internal client attachment command required by B4 is not a new user-facing attach command. Windows batch-file support in B5 does not introduce general shell-expression evaluation or other script/file-association launch support.

## Depends on
None.

## Open questions
The following recommendations are adopted by this draft and remain visible for approval:

- Error status and output: recommend 125 for climon2-owned failures, with the B3 diagnostic prefix and empty stdout except for command output already relayed before a failure. No portable exit code can be disjoint from every possible command status; preserve a command's 125 rather than invent a remapping.
- Home resolution: recommend using only the invoking HOME on Unix or USERPROFILE on Windows for the default `.climon2` location, with the explicit B11 error and no fallback if the required variable is missing or empty. A nonempty CLIMON2_HOME bypasses this lookup. This keeps default-home behavior deterministic and permits isolated acceptance tests without accessing real user state.
- Windows command resolution: recommend PATH-directory order with no implicit current-directory search, then inherited PATHEXT order within each directory for extensionless bare names, with no extra extension defaults. Run `.exe`/`.com` directly and `.cmd`/`.bat` through inherited ComSpec using Rust Command's batch invocation/escaping; refuse unsafe batch arguments with 125 and `cannot launch`. This narrowly scoped shell exception supports command shims without promising general shell evaluation.
- Windows peer identity: availability of `SIO_AF_UNIX_GETPEERPID` on Server 2025 remains unverified (ADR-0003). Recommend native verification as a blocking gate and the specified fail-closed diagnostic; unavailability requires amendment, not an ACL-only fallback.
- Windows protocol test infrastructure: recommend a test-local ctypes/Winsock AF_UNIX helper for S14-S17 because Windows CPython and the current harness do not supply it. If unavailable, require a user-approved harness extension before test delivery, not skipped Windows protocol coverage.
- Cross-user acceptance coverage: every acceptance gate runs tests as one unprivileged user and has no second OS test account, a documented harness gap. Recommend the same-user hello, runtime-directory/socket permission checks and Windows fail-closed diagnostic in S14 as the single-user acceptance coverage. B14's rejection of a different user's connection remains mandatory and is verified by candidate review until the harness gains a second test user; acceptance tests must not attempt connections as another user. These checks do not substitute for the required peer-identity check.
- Install parsing and forwarding: recommend strict SemVer with optional platform newline and real-executable-relative lookup. Recommend preserving empty arguments and redirected stderr, and requiring only stdin/stdout terminals for `exec`.
- Nesting detection and numeric bounds: recommend nonempty inherited CLIMON2_SESSION_ID as the enclosing-session indicator, uint32 positive inherited depths, malformed/missing enclosing depth treated as 1, and an explicit overflow error. Empty CLIMON2_HOME means default; relative overrides resolve against the invoking working directory. Empty XDG_RUNTIME_DIR means fallback; an unsafe configured runtime directory never does.
- Metadata shape: recommend format_version 1, canonical lowercase GUIDs, exact supplied command/arguments, absolute paths, UTC RFC 3339 timestamps, and the runtime's SemVer. Recommend mode 0600/private ACL from first publication. These are representation choices not settled by the field-name list in the brief.
- Protocol wire shape: recommend four-byte big-endian lengths counting UTF-8 JSON payload bytes, protocol field 1, and the B15 hello request/reply. Recommend a fixed acceptance-to-hello deadline, connection closure on invalid frames, and probes that never attach or affect session lifetime. Other terminal-relay message shapes are not frozen by this feature.
- Lifecycle: recommend removing a session's own metadata/socket on orderly exit and client loss, terminating its remaining process group/job, draining final command output, and restoring terminal modes. Observe restoration without test-driven resets using before/after `stty -g` on Unix and subsequent interactive-line echo and execution in the outer shell on Windows, after normal exit and handled failure. On Windows, keep the daemon and command's job outside the launcher's kill-on-close job while the CLI and client remain inside it; forced launcher closure must still allow daemon cleanup. Crash leftovers from an independently crashed/killed daemon remain permitted stale records and `list` must not delete them; launcher or terminal closure is not such an exception. This preserves the brief's temporary disconnect-ends-session rule without changing the glossary's eventual independent lifetime.
- Discovery failures: recommend warning and skipping unreadable/malformed/unsupported records, quietly hiding failed liveness probes and otherwise valid records whose session_id differs from the filename GUID, failing on directory-enumeration errors other than absence, and applying a two-second total deadline per probe. No global listing deadline is imposed for arbitrarily many records.
- Output formats: recommend metadata objects in a JSON array, local second-resolution table timestamps, GUID tie-breaking, platform-independent single-quoted argument display, explicit control/backslash escaping, and an 80-scalar-value ARGS limit including U+2026. JSON must escape the same U+0000-U+001F and U+007F-U+009F ranges as the table, while preserving decoded values. Local-time expectations use the record's instant; recommend TZ-controlled checks only on Unix and the host's actual OS-configured zone with TZ unset on Windows. These settle the brief's unspecified JSON shape, quoting dialect, timestamp precision and truncation boundary without adding flags or configuration.
