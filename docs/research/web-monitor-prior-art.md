# Web monitor prior art: how browser terminals authenticate and where they were broken

Research for [Survey how browser terminals authenticate and where they were broken](https://github.com/jackgeek/climon2/issues/231), part of [Chart the web monitor specification](https://github.com/jackgeek/climon2/issues/229).

Sources were read on 2026-11-14. Source code was read from shallow clones at the commits linked below; every code link is a permalink to that commit. Advisory text was read from the CVE record, the project's own advisory or changelog, or a mirror of it where the canonical page could not be fetched; the "Unverified" section says which.

This is defensive design research. It records root causes and the defence each implies, not exploit steps.

## Summary of conclusions

1. **No surveyed tool gives the web monitor's threat model as it stands.** Each covers a part: Jupyter Server has the most complete loopback defences (random credential, Host check, Origin check, XSRF), Cockpit has the only real server-side sessions and the strictest cookie, VS Code `serve-web` has the best "hostile page in the user's own browser" checks, and sshx is the only one that treats the pipe as hostile. None combines them, and none has per-browser credentials that the user can list and cut off.
2. **The recurring failures are few and repeat across tools.** In order of how often they appear in the advisories read:
   - the credential leaks to another OS user through process arguments or logs (VS Code CVE-2024-26165, Jupyter Notebook 5.7.3, Jupyter Server CVE-2022-24757);
   - a WebSocket or API accepts a cross-origin request because the Origin check is missing or loose (code-server CVE-2023-26114, Jupyter Server CVE-2026-40110, Jupyter Notebook CVE-2016-9971);
   - the server forwards its own credential to something else (code-server CVE-2025-47269 and the 4.124.2 and 4.145.0 fixes);
   - content rendered on the authenticated origin runs script (Jupyter Server CVE-2026-44727, Jupyter Notebook 5.7.1 and 5.7.2, code-server 4.0.1) or the page can be framed (Cockpit CVE-2021-3660);
   - one code path skips the authentication check (ttyd 2017, code-server 4.5.2);
   - unauthenticated input reaches a dangerous sink before the credential is checked (Cockpit CVE-2026-4631);
   - the default has no authentication at all (ttyd CVE-2021-34182, Jupyter Notebook before 4.3).
3. **DNS rebinding is defended by exactly one of the six, and only on loopback.** Jupyter checks the `Host` header against a local allowlist, but turns the check off by default as soon as the server binds a non-loopback address, which is the web monitor's phone case. Comparing `Origin` to `Host`, which ttyd, code-server and Cockpit do, does not stop rebinding because both headers carry the attacker's name. The web monitor needs an explicit allowlist of the names and addresses it is served under, for every bind address.
4. **A shared static secret is the norm, and it is the weak point for lifetime and revocation.** ttyd, code-server, VS Code `serve-web` and Jupyter each have one secret for all browsers. Revocation means restarting the server or changing the password, and every browser is cut off together. The web monitor's "stolen credential equals shell access" stance needs what only Cockpit (server-side session ids) and dev tunnels (scoped, expiring tokens) approach: a credential per browser, held server-side, that can expire and be revoked alone.
5. **The map's known hard problem is confirmed, not solved, by prior art.** sshx and VS Code tunnels both encrypt end to end, and in both the party that relays the traffic also serves the script that holds the key. Neither project claims a defence against that party replacing the script.

## ttyd

Source read at [`2922cb8`](https://github.com/tsl0922/ttyd/tree/2922cb89f518bae4d0fcf4d757a7419638fc71fc).

**Credential.** ttyd has no authentication unless the operator asks for it. `-c USER[:PASSWORD]` enables HTTP Basic authentication, and `-H <name>` hands authentication to a reverse proxy by trusting the presence of a header ([manual](https://github.com/tsl0922/ttyd/blob/2922cb89f518bae4d0fcf4d757a7419638fc71fc/man/ttyd.man.md)). With neither option, `check_auth` returns success for every request ([`http.c` L28-L45](https://github.com/tsl0922/ttyd/blob/2922cb89f518bae4d0fcf4d757a7419638fc71fc/src/http.c#L28-L45)).

**Minting and delivery.** The credential is whatever the operator typed. The page fetches `/token`, and the server answers with the stored Base64 credential itself, not a derived value ([`http.c` L116-L131](https://github.com/tsl0922/ttyd/blob/2922cb89f518bae4d0fcf4d757a7419638fc71fc/src/http.c#L116-L131)). The page then sends it as `AuthToken` in the first WebSocket message, where the server compares it with `strcmp` ([`protocol.c` L300-L350](https://github.com/tsl0922/ttyd/blob/2922cb89f518bae4d0fcf4d757a7419638fc71fc/src/protocol.c#L300-L350)). The WebSocket upgrade must also carry the Basic header ([`protocol.c` L187-L199](https://github.com/tsl0922/ttyd/blob/2922cb89f518bae4d0fcf4d757a7419638fc71fc/src/protocol.c#L187-L199)). At startup the server logs the stored credential, and it logs any token that fails ([`server.c` L142](https://github.com/tsl0922/ttyd/blob/2922cb89f518bae4d0fcf4d757a7419638fc71fc/src/server.c#L142), [`protocol.c` L344](https://github.com/tsl0922/ttyd/blob/2922cb89f518bae4d0fcf4d757a7419638fc71fc/src/protocol.c#L344)).

**Lifetime and revocation.** The credential is fixed for the life of the process. There are no sessions, expiry or revocation. `--once` and `--max-clients` limit how many browsers connect, not which ones ([manual](https://github.com/tsl0922/ttyd/blob/2922cb89f518bae4d0fcf4d757a7419638fc71fc/man/ttyd.man.md)).

**Origin and rebinding.** `-O, --check-origin` is off by default. When on, it rejects a WebSocket whose `Origin` host and port differ from the `Host` header, and rejects a missing `Origin` ([`protocol.c` L51-L72](https://github.com/tsl0922/ttyd/blob/2922cb89f518bae4d0fcf4d757a7419638fc71fc/src/protocol.c#L51-L72), [L227-L232](https://github.com/tsl0922/ttyd/blob/2922cb89f518bae4d0fcf4d757a7419638fc71fc/src/protocol.c#L227-L232)). There is no check of `Host` against an allowlist, so this is not a rebinding defence. The default interface is unset rather than loopback ([`server.c` L321-L322](https://github.com/tsl0922/ttyd/blob/2922cb89f518bae4d0fcf4d757a7419638fc71fc/src/server.c#L321-L322)). Sessions are read-only unless `-W` is given ([manual](https://github.com/tsl0922/ttyd/blob/2922cb89f518bae4d0fcf4d757a7419638fc71fc/man/ttyd.man.md)).

**Published failures.**

- *Authentication bypass, ttyd 1.3.0 and earlier (NCC Group, 2017).* The WebSocket handler checked the token only when the `AuthToken` field was present, so a first message without the field was accepted. Reported, confirmed and patched on 10 March 2017 ([NCC Group advisory](https://nccgroup.com/uk/research-blog/technical-advisory-remote-shell-commands-execution-in-ttyd)). The current code starts every connection unauthenticated and closes it unless the token matches ([`protocol.c` L237](https://github.com/tsl0922/ttyd/blob/2922cb89f518bae4d0fcf4d757a7419638fc71fc/src/protocol.c#L237), [L337-L350](https://github.com/tsl0922/ttyd/blob/2922cb89f518bae4d0fcf4d757a7419638fc71fc/src/protocol.c#L337-L350)). Root cause: authentication expressed as "reject if the supplied value is wrong" rather than "accept only if a correct value was supplied".
- *CVE-2021-34182.* The record describes arbitrary code execution in ttyd 1.6.3 "via default configuration permissions", classed as CWE-276, and references ttyd issue 692 ([NVD](https://nvd.nist.gov/vuln/detail/CVE-2021-34182)). Root cause: a shell with no credential is the default.

**For the web monitor.** ttyd gives nothing to copy for authentication. It is the cautionary baseline: opt-in authentication, a credential that is a human-chosen password echoed back by an endpoint and written to the log, an opt-in Origin check, and no notion of which browser is connected. Its one transferable idea is authenticating inside the WebSocket with the first message, which does not depend on cookies.

## code-server

Source read at [`dda09f2`](https://github.com/coder/code-server/tree/dda09f22fa51926c6c9c8a9fc26a6ad00759b2dc).

**Credential.** One password for the whole server, on by default. `--auth none` turns it off ([FAQ](https://github.com/coder/code-server/blob/dda09f22fa51926c6c9c8a9fc26a6ad00759b2dc/docs/FAQ.md), [guide](https://github.com/coder/code-server/blob/dda09f22fa51926c6c9c8a9fc26a6ad00759b2dc/docs/guide.md)).

**Minting and delivery.** On first run code-server writes a config file with a generated password of 24 hex characters from the system random source and a default bind address of `127.0.0.1:8080` ([`util.ts` L134-L138](https://github.com/coder/code-server/blob/dda09f22fa51926c6c9c8a9fc26a6ad00759b2dc/src/node/util.ts#L134-L138), [`cli.ts` L759-L800](https://github.com/coder/code-server/blob/dda09f22fa51926c6c9c8a9fc26a6ad00759b2dc/src/node/cli.ts#L759-L800)). The user copies it from the file into a login form. On success the server sets a cookie whose value is an Argon2 hash of the password; the code comments that the hash "does not add any actual security" and is there for obfuscation ([`login.ts` L88-L93](https://github.com/coder/code-server/blob/dda09f22fa51926c6c9c8a9fc26a6ad00759b2dc/src/node/routes/login.ts#L88-L93)). The cookie is validated by verifying that hash against the configured password, so it is a function of the password alone ([`util.ts` L272-L291](https://github.com/coder/code-server/blob/dda09f22fa51926c6c9c8a9fc26a6ad00759b2dc/src/node/util.ts#L272-L291)).

**Lifetime and revocation.** The cookie options are domain, path, `SameSite=Lax` and `HttpOnly`, with no expiry, so it is a browser-session cookie ([`http.ts` L311-L335](https://github.com/coder/code-server/blob/dda09f22fa51926c6c9c8a9fc26a6ad00759b2dc/src/node/http.ts#L311-L335)). The server keeps no session table. A captured cookie stays valid until the password changes, and changing the password cuts off every browser. Login attempts are limited to two per minute plus twelve per hour, globally rather than per client ([`login.ts` L10-L27](https://github.com/coder/code-server/blob/dda09f22fa51926c6c9c8a9fc26a6ad00759b2dc/src/node/routes/login.ts#L10-L27)).

**Origin and rebinding.** WebSocket upgrades pass through `ensureOrigin` before the authentication check. It allows a missing `Origin`, allows an origin on the `--trusted-origins` list, and otherwise requires the origin's host to match the request host, taken from `Forwarded`, `X-Forwarded-Host` or `Host` ([`http.ts` L386-L427](https://github.com/coder/code-server/blob/dda09f22fa51926c6c9c8a9fc26a6ad00759b2dc/src/node/http.ts#L386-L427), [`vscode.ts` L245](https://github.com/coder/code-server/blob/dda09f22fa51926c6c9c8a9fc26a6ad00759b2dc/src/node/routes/vscode.ts#L245)). There is no Host allowlist. The project's own guidance is to never expose code-server directly to the internet and to prefer SSH port forwarding ([guide](https://github.com/coder/code-server/blob/dda09f22fa51926c6c9c8a9fc26a6ad00759b2dc/docs/guide.md)).

**Published failures.** All from the project's [changelog](https://github.com/coder/code-server/blob/dda09f22fa51926c6c9c8a9fc26a6ad00759b2dc/CHANGELOG.md) unless linked otherwise.

- *CVE-2023-26114, fixed in 4.10.1.* WebSocket handshakes had no Origin validation ([GHSA-frjg-g767-7363 via OSV](https://osv.dev/vulnerability/GHSA-frjg-g767-7363)). The changelog says the check was added "to prevent cross-site hijacking attacks on users using older or niche browser that do not support SameSite cookies and attacks across sub-domains that share the same root domain". Root cause: relying on `SameSite` alone to keep a cookie-authenticated WebSocket same-origin. `SameSite` is about sites, not origins, so a sibling subdomain is inside it.
- *CVE-2025-47269, fixed in 4.99.4.* The built-in port proxy did not validate that the port in the path was a number, so a request could be proxied to an arbitrary domain and carry the session cookie with it ([GHSA-p483-wpfp-42cj, read via a mirror](https://corgea.com/advisories/vulnerabilities/CVE-2025-47269)). Root cause: a server-side forwarder that attaches the user's credential, driven by an unvalidated URL component.
- *4.124.2 (2026-06-16).* The session cookie was sent on to the proxied local port, so a local service running as a different user could capture it and log in. *4.145.0 (2026-11-04)* fixed the same leak for proxied WebSockets and added `HttpOnly`. Root cause: the credential's scope (code-server) was narrower than where it was sent (anything behind the proxy).
- *4.5.2 (2022-08-15).* The proxy route performed no authentication. Root cause: authentication applied per route, with one route missed.
- *4.0.1 (2022-01-04).* XSS through unescaped messages in the error page.

**For the web monitor.** The useful parts are small: generate the secret rather than accept a chosen one, bind loopback by default, rate-limit attempts, and run the Origin check before the credential check on every upgrade. What it does not give: a cookie that is the password in another form cannot be revoked per browser and never expires server-side; `SameSite=Lax` plus an Origin-equals-Host comparison leaves rebinding open; and the proxy history shows that any feature which makes the server speak to a third party on the user's behalf becomes a credential leak. The web monitor should have no such feature.

## VS Code `serve-web` and tunnels

Source read at [`9bfb9e7`](https://github.com/microsoft/vscode/tree/9bfb9e7eefb447fcb013761b1b18e861d3d320b2).

### `serve-web`

**Credential.** A single connection token. `--without-connection-token` disables it, described as "Only use this if the connection is secured by other means" ([`args.rs`](https://github.com/microsoft/vscode/blob/9bfb9e7eefb447fcb013761b1b18e861d3d320b2/cli/src/commands/args.rs#L195-L213)).

**Minting and delivery.** The CLI creates a file `serve-web-token` with mode `0600`, reuses its contents if it is not empty, and otherwise writes a new version-4 UUID ([`serve_web.rs` L1037-L1062](https://github.com/microsoft/vscode/blob/9bfb9e7eefb447fcb013761b1b18e861d3d320b2/cli/src/commands/serve_web.rs#L1037-L1062)). It prints the URL with `?tkn=<token>` and passes the token to the server by file, never by argument ([`serve_web.rs` L161-L163](https://github.com/microsoft/vscode/blob/9bfb9e7eefb447fcb013761b1b18e861d3d320b2/cli/src/commands/serve_web.rs#L161-L163), [L926-L933](https://github.com/microsoft/vscode/blob/9bfb9e7eefb447fcb013761b1b18e861d3d320b2/cli/src/commands/serve_web.rs#L926-L933)). The server component does the same when run alone, storing the UUID in `<user-data-dir>/token` ([`serverConnectionToken.ts` L97-L125](https://github.com/microsoft/vscode/blob/9bfb9e7eefb447fcb013761b1b18e861d3d320b2/src/vs/server/node/serverConnectionToken.ts#L97-L125)). A request with the token in the query gets it set as the `vscode-tkn` cookie and is redirected to a URL without it ([`webClientServer.ts` L334-L349](https://github.com/microsoft/vscode/blob/9bfb9e7eefb447fcb013761b1b18e861d3d320b2/src/vs/server/node/webClientServer.ts#L334-L349)). The WebSocket is authenticated again by a first message of type `auth` carrying the token ([`remoteExtensionHostAgentServer.ts` L300-L310](https://github.com/microsoft/vscode/blob/9bfb9e7eefb447fcb013761b1b18e861d3d320b2/src/vs/server/node/remoteExtensionHostAgentServer.ts#L300-L310)).

**Lifetime and revocation.** The CLI sets the cookie with `SameSite=Strict; Max-Age=2592000` (30 days); the server sets it with `SameSite=Lax` and one week ([`serve_web.rs` L306-L315](https://github.com/microsoft/vscode/blob/9bfb9e7eefb447fcb013761b1b18e861d3d320b2/cli/src/commands/serve_web.rs#L306-L315), [`webClientServer.ts` L342-L348](https://github.com/microsoft/vscode/blob/9bfb9e7eefb447fcb013761b1b18e861d3d320b2/src/vs/server/node/webClientServer.ts#L342-L348)). Neither sets `HttpOnly`; the page's script needs the token for the WebSocket message. The cookie value is the token itself, and the token is reused across runs, so nothing expires server-side and revocation means deleting the token file and restarting.

**Origin and rebinding.** The CLI binds `localhost` unless `--host` is given ([`serve_web.rs` L140-L144](https://github.com/microsoft/vscode/blob/9bfb9e7eefb447fcb013761b1b18e861d3d320b2/cli/src/commands/serve_web.rs#L140-L144)). When the token arrives only as a cookie, the CLI rejects the request if `Sec-Fetch-Site` is `cross-site` or `same-site`; a token in the query is accepted regardless ([`serve_web.rs` L317-L345](https://github.com/microsoft/vscode/blob/9bfb9e7eefb447fcb013761b1b18e861d3d320b2/cli/src/commands/serve_web.rs#L317-L345)). Every response carries `Content-Security-Policy: frame-ancestors 'self'` and `X-Frame-Options: SAMEORIGIN` ([`serve_web.rs` L292-L304](https://github.com/microsoft/vscode/blob/9bfb9e7eefb447fcb013761b1b18e861d3d320b2/cli/src/commands/serve_web.rs#L292-L304)). No Host allowlist was found in `serve_web.rs`.

**Published failure.** *CVE-2024-26165, fixed in 1.87.2.* A lower-privileged account on the same machine that could view process information could obtain the connection token protecting a `serve-web` server run by another account; the fix moved the token into a file with restrictive permissions ([GHSA-54p6-6j68-j5vr](https://www.github.com/microsoft/vscode/security/advisories/GHSA-54p6-6j68-j5vr)). Root cause: a secret on a command line is readable by every OS user.

### Tunnels

**Credential.** An account, not a secret the tool mints. Both hosting and connecting require signing in with the same GitHub or Microsoft account ([VS Code tunnels documentation](https://code.visualstudio.com/docs/remote/tunnels)). The CLI uses the OAuth device-code flow against `github.com/login/device/code` or `login.microsoftonline.com`, and stores the resulting tokens in the OS keyring ([`auth.rs` L65-L98](https://github.com/microsoft/vscode/blob/9bfb9e7eefb447fcb013761b1b18e861d3d320b2/cli/src/auth.rs#L65-L98), [L305-L345](https://github.com/microsoft/vscode/blob/9bfb9e7eefb447fcb013761b1b18e861d3d320b2/cli/src/auth.rs#L305-L345)).

**Lifetime and revocation.** The dev tunnels service issues tunnel-scoped access tokens of four kinds (client, host, manage-ports, management) that expire, currently after 24 hours ([dev tunnels security documentation](https://learn.microsoft.com/th-th/azure/developer/dev-tunnels/security)). A machine is reachable only while the CLI runs there, and `code tunnel unregister` removes its tunnel ([VS Code tunnels documentation](https://code.visualstudio.com/docs/remote/tunnels)).

**Transport.** Tunnels and their ports are private to the creating account by default ([dev tunnels security documentation](https://learn.microsoft.com/th-th/azure/developer/dev-tunnels/security)). VS Code opens an SSH connection inside the tunnel for end-to-end encryption, preferring AES-256 in CTR mode ([VS Code tunnels documentation](https://code.visualstudio.com/docs/remote/tunnels)). For web-forwarded ports the service terminates TLS at its own ingress with its own certificates and rewrites headers after termination ([dev tunnels security documentation](https://learn.microsoft.com/th-th/azure/developer/dev-tunnels/security)).

**Published failures.** None found that concern tunnel authentication itself.

**For the web monitor.** `serve-web` contributes three concrete defences: exchange a URL credential for a cookie and redirect to a clean URL at once; refuse a cookie-only request whose `Sec-Fetch-Site` says it did not come from the same origin; and keep the secret in a `0600` file, never in arguments. It does not give revocation (one long-lived token reused across runs), `HttpOnly` (script reads the token), or a rebinding defence. Tunnels show what the map already excludes: identity delegated to a third-party account and reachability delegated to a relay that terminates TLS for browsers. The end-to-end SSH layer protects native VS Code clients; a browser gets its script from `vscode.dev` and its TLS from the service, so the pipe is trusted there.

## Jupyter Server

Source read at [`0d1a13b`](https://github.com/jupyter-server/jupyter_server/tree/0d1a13b2f5212a9f9da0122a9e7dbaf23f6cfcb7). Jupyter Notebook history is from the [Notebook changelog](https://jupyter-notebook.readthedocs.io/en/5.7.6/changelog.html).

**Credential.** Token authentication is on by default; setting a password turns the token off by default ([security documentation](https://github.com/jupyter-server/jupyter_server/blob/0d1a13b2f5212a9f9da0122a9e7dbaf23f6cfcb7/docs/source/operators/security.rst)). Token authentication arrived in Notebook 4.3.0; before that a local server had none ([Notebook changelog](https://jupyter-notebook.readthedocs.io/en/5.7.6/changelog.html)).

**Minting and delivery.** The token is 24 bytes from `os.urandom`, hex-encoded, generated at each start unless `JUPYTER_TOKEN` or `JUPYTER_TOKEN_FILE` supplies one ([`identity.py` L209-L224](https://github.com/jupyter-server/jupyter_server/blob/0d1a13b2f5212a9f9da0122a9e7dbaf23f6cfcb7/jupyter_server/auth/identity.py#L209-L224)). It is accepted in an `Authorization: token` header, a `?token=` query parameter, or the login form, and is printed in the terminal as part of the URL ([security documentation](https://github.com/jupyter-server/jupyter_server/blob/0d1a13b2f5212a9f9da0122a9e7dbaf23f6cfcb7/docs/source/operators/security.rst)). To open the browser the server writes an HTML file that redirects to the URL with the token, instead of passing that URL as a browser argument ([`serverapp.py` L3020-L3028](https://github.com/jupyter-server/jupyter_server/blob/0d1a13b2f5212a9f9da0122a9e7dbaf23f6cfcb7/jupyter_server/serverapp.py#L3020-L3028)). Notebook 5.7.3 introduced this so that another logged-in user could not read the token from the command line ([Notebook changelog](https://jupyter-notebook.readthedocs.io/en/5.7.6/changelog.html)). After a token-authenticated request the server sets a signed cookie, `HttpOnly` by default and `Secure` when the request came over HTTPS ([`identity.py` L388-L400](https://github.com/jupyter-server/jupyter_server/blob/0d1a13b2f5212a9f9da0122a9e7dbaf23f6cfcb7/jupyter_server/auth/identity.py#L388-L400)).

**Lifetime and revocation.** The token is compared with `==` on each request and lives as long as the server ([`identity.py` L484-L504](https://github.com/jupyter-server/jupyter_server/blob/0d1a13b2f5212a9f9da0122a9e7dbaf23f6cfcb7/jupyter_server/auth/identity.py#L484-L504)). The server keeps no session table: the documentation says it relies on the cookie to carry identity ([security documentation](https://github.com/jupyter-server/jupyter_server/blob/0d1a13b2f5212a9f9da0122a9e7dbaf23f6cfcb7/docs/source/operators/security.rst)). There is no per-browser revocation.

**Origin and rebinding.**

- *Host check.* When `allow_remote_access` is false, a request whose `Host` is neither a loopback address nor in `local_hostnames` (default `localhost`) is refused ([`handlers.py` L556-L594](https://github.com/jupyter-server/jupyter_server/blob/0d1a13b2f5212a9f9da0122a9e7dbaf23f6cfcb7/jupyter_server/base/handlers.py#L556-L594)). The option's help text names DNS rebinding as the reason. It defaults to true, disabling the check, whenever the server listens on a non-loopback address ([`serverapp.py` L1352-L1396](https://github.com/jupyter-server/jupyter_server/blob/0d1a13b2f5212a9f9da0122a9e7dbaf23f6cfcb7/jupyter_server/serverapp.py#L1352-L1396)). Notebook 5.7.0 added it as "a pre-emptive measure, not fixing a known vulnerability" ([Notebook changelog](https://jupyter-notebook.readthedocs.io/en/5.7.6/changelog.html)).
- *Origin check.* For API requests and WebSockets, `Origin` must equal `Host` or match `allow_origin` or `allow_origin_pat`. A missing `Origin` is allowed, and the check is skipped for token-authenticated requests, since a hostile page cannot supply the token ([`handlers.py` L437-L482](https://github.com/jupyter-server/jupyter_server/blob/0d1a13b2f5212a9f9da0122a9e7dbaf23f6cfcb7/jupyter_server/base/handlers.py#L437-L482), [`identity.py` L533-L542](https://github.com/jupyter-server/jupyter_server/blob/0d1a13b2f5212a9f9da0122a9e7dbaf23f6cfcb7/jupyter_server/auth/identity.py#L533-L542)).
- *XSRF.* Cookie-authenticated requests need the XSRF token; for GET a same-host `Referer` is accepted instead ([`handlers.py` L484-L554](https://github.com/jupyter-server/jupyter_server/blob/0d1a13b2f5212a9f9da0122a9e7dbaf23f6cfcb7/jupyter_server/base/handlers.py#L484-L554)).
- *Framing.* The default policy is `frame-ancestors 'self'` ([`handlers.py` L94-L117](https://github.com/jupyter-server/jupyter_server/blob/0d1a13b2f5212a9f9da0122a9e7dbaf23f6cfcb7/jupyter_server/base/handlers.py#L94-L117)).

The default bind address is `localhost` ([`serverapp.py` L1014-L1021](https://github.com/jupyter-server/jupyter_server/blob/0d1a13b2f5212a9f9da0122a9e7dbaf23f6cfcb7/jupyter_server/serverapp.py#L1014-L1021)).

**Published failures.**

- *CVE-2026-40110, fixed in 2.18.0.* `allow_origin_pat` was applied with `re.match`, which anchors only at the start, so an origin that merely began with a trusted name passed ([advisory GHSA-24qx-w28j-9m6p, read via the GitLab advisory database](https://advisories.gitlab.com/pypi/jupyter-server/CVE-2026-40110/)). The current code uses `re.fullmatch` and cites the advisory ([`utils.py` L46-L58](https://github.com/jupyter-server/jupyter_server/blob/0d1a13b2f5212a9f9da0122a9e7dbaf23f6cfcb7/jupyter_server/utils.py#L46-L58)). Root cause: origin allowlisting by pattern instead of exact comparison.
- *CVE-2022-24757, fixed in 1.15.4.* On a 5xx error the server logged request headers including the authentication cookie, and the logs were readable without root ([Debian security tracker entry quoting the advisory](https://security-tracker.debian.org/tracker/CVE-2022-24757)). Root cause: a credential written to a diagnostic log.
- *CVE-2023-40170, fixed in 2.7.2.* Cross-site credential checks on `/files/` URLs were incomplete, allowing some file contents to be included by another site; the earlier Notebook fix had not been fully carried over ([GHSA-64x5-55rw-9974](https://github.com/advisories/GHSA-64x5-55rw-9974)). Notebook 5.7.6 had fixed the original by setting `X-Content-Type-Options: nosniff` and extending CSRF checks to GET on the API and `/files/` ([Notebook changelog](https://jupyter-notebook.readthedocs.io/en/5.7.6/changelog.html)). Root cause: GET requests treated as safe when their responses carry secrets.
- *CVE-2026-44727, fixed in 2.20.0.* nbconvert handlers served notebook-authored HTML on the Jupyter origin without a CSP `sandbox`, so script in a notebook's output ran with the user's authority ([advisory GHSA-fcw5-x6j4-ccmp, read via the GitLab advisory database](https://advisories.gitlab.com/pypi/jupyter-server/CVE-2026-44727/)). The handlers now add `sandbox allow-scripts` ([`nbconvert/handlers.py` L99-L100](https://github.com/jupyter-server/jupyter_server/blob/0d1a13b2f5212a9f9da0122a9e7dbaf23f6cfcb7/jupyter_server/nbconvert/handlers.py#L99-L100)). Notebook 5.7.1 and 5.7.2 fixed the same class ([Notebook changelog](https://jupyter-notebook.readthedocs.io/en/5.7.6/changelog.html)). Root cause: untrusted content rendered as active content on the authenticated origin.
- *CVE-2020-26232, fixed in 1.0.6.* Open redirect ([changelog](https://github.com/jupyter-server/jupyter_server/blob/0d1a13b2f5212a9f9da0122a9e7dbaf23f6cfcb7/CHANGELOG.md)).
- *CVE-2016-9971, Notebook 4.3.1.* A cross-site form could create files and start kernels in browsers that sent no `Origin` on such posts ([Notebook changelog](https://jupyter-notebook.readthedocs.io/en/5.7.6/changelog.html)). Root cause: treating a missing `Origin` as same-origin for a state-changing request.

**For the web monitor.** Jupyter is the closest model for loopback use and the best source of defaults: a high-entropy credential minted per start, delivered without touching process arguments, and layered with Host, Origin and XSRF checks. Three things do not carry over. The Host check is off exactly when the server is reachable from another device. The token is one shared secret with no revocation short of a restart. And its advisory record shows how hard it is to keep an authenticated origin clean when it renders user-controlled content, which for the web monitor is session output and titles.

## sshx

Source read at [`3604e8e`](https://github.com/ekzhang/sshx/tree/3604e8ec5ce0e741bd4a7de2e339b980ca8a2d40).

**Credential.** The link is the credential. It has the form `<origin>/s/<name>#<key>`, with `,<write password>` appended when read-only mode is enabled ([`controller.rs` L57-L96](https://github.com/ekzhang/sshx/blob/3604e8ec5ce0e741bd4a7de2e339b980ca8a2d40/crates/sshx/src/controller.rs#L57-L96)). There are no accounts and no cookies.

**Minting and delivery.** The CLI on the user's machine generates the key and the optional write password, each 14 random alphanumeric characters, which the code rates at 83.3 bits; the server generates the 10-character session name ([`controller.rs` L57-L70](https://github.com/ekzhang/sshx/blob/3604e8ec5ce0e741bd4a7de2e339b980ca8a2d40/crates/sshx/src/controller.rs#L57-L70), [`grpc.rs` L51-L69](https://github.com/ekzhang/sshx/blob/3604e8ec5ce0e741bd4a7de2e339b980ca8a2d40/crates/sshx-server/src/grpc.rs#L51-L69)). The key is stretched with Argon2id under a fixed public salt into an AES-128 key, and terminal data is encrypted with AES-128 in CTR mode ([`encrypt.rs` L7-L33](https://github.com/ekzhang/sshx/blob/3604e8ec5ce0e741bd4a7de2e339b980ca8a2d40/crates/sshx/src/encrypt.rs#L7-L33), [L46-L59](https://github.com/ekzhang/sshx/blob/3604e8ec5ce0e741bd4a7de2e339b980ca8a2d40/crates/sshx/src/encrypt.rs#L46-L59)). The server never receives the key. It stores the encryption of a zero block as a verifier, and a browser proves knowledge of the key by presenting the same value, compared in constant time ([`socket.rs` L99-L128](https://github.com/ekzhang/sshx/blob/3604e8ec5ce0e741bd4a7de2e339b980ca8a2d40/crates/sshx-server/src/web/socket.rs#L99-L128)). The browser reads the key from `location.hash`, which browsers do not send to servers ([`Session.svelte` L133-L135](https://github.com/ekzhang/sshx/blob/3604e8ec5ce0e741bd4a7de2e339b980ca8a2d40/src/lib/Session.svelte#L133-L135)). The user moves the link to the browser by hand.

**Lifetime and revocation.** The link is valid while the CLI process runs; a session with no connection is closed after 5 minutes ([`state.rs` L22-L27](https://github.com/ekzhang/sshx/blob/3604e8ec5ce0e741bd4a7de2e339b980ca8a2d40/crates/sshx-server/src/state.rs#L22-L27)). There is no rotation and no way to cut off one browser.

**Origin and rebinding.** No Origin or Host check was found in the server crate. With no cookie there is no ambient credential, so a hostile page cannot act for the user without the link.

**Published failures.** No advisory found. Two limits are visible in the source rather than in an advisory. The encryption is unauthenticated CTR mode, so the relay cannot read the stream but nothing in the cipher detects modification. And the same server that relays ciphertext serves the page and script that read the key from the fragment. The README states that self-hosting is unsupported and that running the development setup in public is insecure ([README](https://github.com/ekzhang/sshx/blob/3604e8ec5ce0e741bd4a7de2e339b980ca8a2d40/README.md)).

**For the web monitor.** sshx gives two ideas worth keeping. A credential in the URL fragment is never sent in a request line, so it stays out of server logs, proxies and `Referer`. And a credential that is not a cookie removes cross-site request forgery and cross-site WebSocket hijacking as classes, because the browser never attaches it on its own. What it does not give: a bearer link is the opposite of per-browser revocation, anyone who sees the link once has full control, and the end-to-end claim rests on trusting the server's script, which is the map's known hard problem unchanged.

## Cockpit

Source read at [`8151774`](https://github.com/cockpit-project/cockpit/tree/81517745c50d4be3e30403c9bcc2f6ce9d226b14).

**Credential.** The OS account's own credentials. `cockpit-ws` hands the user name and password to `cockpit-session`, which opens a PAM session, relays any further PAM prompts such as a second factor, and then runs the bridge as that user ([`doc/authentication.md` L215-L222](https://github.com/cockpit-project/cockpit/blob/81517745c50d4be3e30403c9bcc2f6ce9d226b14/doc/authentication.md)). Kerberos, TLS client certificates and an OAuth bearer flow are alternatives ([authentication guide](https://github.com/cockpit-project/cockpit/blob/81517745c50d4be3e30403c9bcc2f6ce9d226b14/doc/modules/guide/pages/authentication.adoc), [`cockpit.conf` manual](https://github.com/cockpit-project/cockpit/blob/81517745c50d4be3e30403c9bcc2f6ce9d226b14/doc/modules/man/pages/cockpit.conf.5.adoc)).

**Minting and delivery.** After a successful login the server mints a session id as an HMAC-SHA256 over a counter under a random per-process key, and sets it as a cookie with `Path=/; SameSite=Strict; HttpOnly`, plus `Secure` on TLS ([`cockpitauth.c` L300-L310](https://github.com/cockpit-project/cockpit/blob/81517745c50d4be3e30403c9bcc2f6ce9d226b14/src/ws/cockpitauth.c#L300-L310), [L1569-L1586](https://github.com/cockpit-project/cockpit/blob/81517745c50d4be3e30403c9bcc2f6ce9d226b14/src/ws/cockpitauth.c#L1569-L1586)). The cookie holds only the id; the session itself is a server-side table entry.

**Lifetime and revocation.** Each login is its own session. `IdleTimeout` logs out an inactive interactive session and is off unless set; `MaxStartups` and `MaxConcurrentConnections` bound unauthenticated load ([`cockpit.conf` manual](https://github.com/cockpit-project/cockpit/blob/81517745c50d4be3e30403c9bcc2f6ce9d226b14/doc/modules/man/pages/cockpit.conf.5.adoc)). Logging out destroys the server-side entry, so one browser can be cut off without touching the others.

**Origin and rebinding.** By default a WebSocket is accepted only from the origin made of the request's own scheme and host; `Origins` in `cockpit.conf` replaces that default with a list matched by `fnmatch` ([`cockpitwebservice.c` L1297-L1322](https://github.com/cockpit-project/cockpit/blob/81517745c50d4be3e30403c9bcc2f6ce9d226b14/src/ws/cockpitwebservice.c#L1297-L1322), [`cockpit.conf` manual](https://github.com/cockpit-project/cockpit/blob/81517745c50d4be3e30403c9bcc2f6ce9d226b14/doc/modules/man/pages/cockpit.conf.5.adoc)). Channel requests made outside the WebSocket carry a per-session CSRF token in the path ([`cockpithandlers.c` L149-L174](https://github.com/cockpit-project/cockpit/blob/81517745c50d4be3e30403c9bcc2f6ce9d226b14/src/ws/cockpithandlers.c#L149-L174)). Responses set `Referrer-Policy: no-referrer`, `Cross-Origin-Resource-Policy: same-origin` and `X-Frame-Options: sameorigin` ([`cockpitwebresponse.c` L850-L861](https://github.com/cockpit-project/cockpit/blob/81517745c50d4be3e30403c9bcc2f6ce9d226b14/src/ws/cockpitwebresponse.c#L850-L861)). Plain HTTP is redirected to HTTPS except from localhost unless `AllowUnencrypted` is set ([`cockpit.conf` manual](https://github.com/cockpit-project/cockpit/blob/81517745c50d4be3e30403c9bcc2f6ce9d226b14/doc/modules/man/pages/cockpit.conf.5.adoc)). The default origin is built from the request's own `Host`, so there is no Host allowlist.

**Published failures.**

- *CVE-2026-4631, Cockpit 326 to 359, fixed in 360.* The remote-login feature passed a host name and user name from the login request to the `ssh` client without validation, which allowed code execution on the Cockpit host without valid credentials. Disabling `LoginTo` removes the exposed feature ([Cockpit 360 release notes](https://cockpit-project.org/blog/cockpit-360.html), [oss-security post](https://openwall.com/lists/oss-security/2026/04/10/5)). Root cause: input from an unauthenticated request used to build a command line during the authentication flow itself.
- *CVE-2021-3660.* Cockpit pages could be rendered inside a frame on another site ([CVE description as mirrored by Tenable](https://tenable.com/cve/CVE-2021-3660)). The current code sends `X-Frame-Options: sameorigin`. Root cause: no framing policy on a page whose clicks carry authority.
- *CVE-2024-2947, fixed in 314.* Deleting a diagnostic report built a shell command from a file name that an unprivileged user could choose; the fix uses direct system calls ([Cockpit 314 release notes](https://cockpit-project.org/blog/cockpit-314.html)).
- *CVE-2024-6126.* An authenticated user could kill arbitrary processes when `pam_env`'s `user_readenv` was enabled ([CVE record](https://cveawg.mitre.org/api/cve/CVE-2024-6126)).

**For the web monitor.** Cockpit is the model for the session layer: a server-side session per browser, an opaque id in a `SameSite=Strict; HttpOnly; Secure` cookie, an exact Origin check on the WebSocket, a second CSRF token for anything outside it, and conservative response headers. Its login does not carry over. A password typed into a browser form proves knowledge of the account password, not "already acting as that OS user on the serving machine", and it puts a reusable OS credential on the wire and in the page. CVE-2026-4631 is the strongest single lesson in this survey for the web monitor: the pairing path is the only code an attacker without a credential can reach, so it must take the least input and do the least with it.

## Lessons for the web monitor's threat model

Each lesson names the threat-model actor from the map it bears on.

**Anyone who can reach the port**

1. *No mode without a credential.* ttyd's default and Notebook before 4.3 show what a shell-capable port without one becomes ([NVD](https://nvd.nist.gov/vuln/detail/CVE-2021-34182), [Notebook changelog](https://jupyter-notebook.readthedocs.io/en/5.7.6/changelog.html)). VS Code and code-server both keep an escape hatch (`--without-connection-token`, `--auth none`); given the web view's full authority, the web monitor should not.
2. *Authenticate by default-deny, in one place.* ttyd's 2017 bypass and code-server 4.5.2 were both a path that the check did not cover ([NCC Group](https://nccgroup.com/uk/research-blog/technical-advisory-remote-shell-commands-execution-in-ttyd), [code-server changelog](https://github.com/coder/code-server/blob/dda09f22fa51926c6c9c8a9fc26a6ad00759b2dc/CHANGELOG.md)). Every route and every upgrade should pass one gate, with the unauthenticated exceptions listed explicitly.
3. *Keep the pre-credential surface minimal.* Cockpit CVE-2026-4631 came from doing real work with request fields before authentication finished ([Cockpit 360 release notes](https://cockpit-project.org/blog/cockpit-360.html)). The pairing exchange should parse fixed-size, fixed-format input and touch nothing else.
4. *Mint the credential; never accept a chosen one.* Jupyter (192 bits), VS Code (a UUID) and code-server (96 bits) generate theirs; ttyd takes a human password. Bound attempts as code-server and Cockpit do, because a pairing code typed on a phone will be short.

**Other OS users on the same machine**

5. *The credential must never be in process arguments, environment of other processes, or logs.* CVE-2024-26165, Notebook 5.7.3 and CVE-2022-24757 are the same mistake three times ([VS Code advisory](https://www.github.com/microsoft/vscode/security/advisories/GHSA-54p6-6j68-j5vr), [Notebook changelog](https://jupyter-notebook.readthedocs.io/en/5.7.6/changelog.html), [Debian tracker](https://security-tracker.debian.org/tracker/CVE-2022-24757)). ttyd still logs its credential. This binds the map's "Diagnostics and audit" item: the general log may record that pairing happened, never the secret, cookie or full URL.
6. *Anything stored is `0600` in a private directory*, as VS Code's token file and Jupyter's cookie secret are. On a shared machine a loopback port is reachable by every OS user, so loopback binding is not an access control; only the credential is.

**Anyone on the network path**

7. *A URL credential must be single-purpose and short-lived.* VS Code and Jupyter both put a long-lived secret in the query string and then scrub it by redirect. sshx's fragment is better, since it is never sent. Either way the long-lived credential should be something the server issues after pairing, not the thing in the URL. Cockpit's `Referrer-Policy: no-referrer` is a cheap companion.
8. *End-to-end encryption does not survive a server that also serves the script.* sshx and tunnels both show it. The survey found no prior art that solves the map's known hard problem; the TLS research ticket has to.

**Hostile pages in the user's own browser**

9. *Treat a cookie as ambient and defend it four ways.* `SameSite=Strict; HttpOnly; Secure` (Cockpit), an exact Origin check on every WebSocket upgrade before authentication (code-server since CVE-2023-26114), rejection of cookie-only requests whose `Sec-Fetch-Site` is not `same-origin` (VS Code `serve-web`), and a second non-cookie proof inside the WebSocket (VS Code's first `auth` message, ttyd's `AuthToken`, Cockpit's CSRF token). `SameSite` alone failed for code-server because it is scoped to the site, not the origin. Cookies are also not isolated by port ([RFC 6265 section 8.5](https://www.rfc-editor.org/rfc/rfc6265#section-8.5)), so on `localhost` any other local web server shares the web monitor's cookie jar; a host-only cookie with the `__Host-` prefix and a server-side session id limits what that exposes.
10. *Compare origins exactly against a list.* Jupyter's CVE-2026-40110 came from a pattern match, and Cockpit's `Origins` uses `fnmatch`. The web monitor knows the exact origins it serves; it needs string equality and no wildcard option. A missing `Origin` on a WebSocket upgrade should be refused, not waved through as code-server and Jupyter do for non-browser clients, because the web view is the only client.
11. *Check `Host` against an allowlist on every request, for every bind address.* This is the only rebinding defence in the survey, and Jupyter disables it for non-loopback binds. The web monitor should know the names and addresses it is reachable at (loopback, the configured LAN address or name) and refuse any other `Host`. TLS with a certificate for the real name also defeats rebinding, since the attacker's name will not validate.
12. *Forbid framing outright*, `frame-ancestors 'none'`, after Cockpit CVE-2021-3660.

**Session output and titles as untrusted input**

13. *Nothing from a session may become markup or script on the authenticated origin.* Jupyter's nbconvert advisories, Notebook 5.7.1 and 5.7.2, and code-server 4.0.1 are all "content the tool displays ran as the tool". For the web view this means session titles and any text in toasts and the selector are set as text, never as HTML; a strict CSP with no inline script and no third-party origins; and `X-Content-Type-Options: nosniff`. This binds the map's "Asset delivery and page hardening" item.
14. *No forwarding features.* Every credential leak in code-server's history came from its port proxy. The web monitor should serve its own assets and its own WebSocket and nothing else.

**Lifetime and revocation**

15. *Per-browser, server-side credentials.* Four of six tools have one static secret and can only revoke everyone by restarting. The map's "Diagnostics and audit" item (see who is connected and cut them off) requires Cockpit's shape: a session table in the web monitor, an opaque id per browser, expiry enforced server-side, and revocation of one entry. Dev tunnels' expiring scoped tokens show the same idea at service scale.
16. *Decide deliberately whether a credential survives a restart.* VS Code reuses its token file across runs for convenience; Jupyter mints a fresh token each start. For "stolen credential equals shell access", surviving a restart is a convenience that needs an explicit decision in the pairing ticket.
17. *Compare secrets in constant time.* sshx and code-server do; ttyd, VS Code and Jupyter use plain equality. With high-entropy secrets the exposure is small, and the fix costs nothing.

### What each design would and would not give the web monitor

| Design | Would give | Would not give |
|---|---|---|
| ttyd (Basic password, token echo) | Nothing beyond in-band WebSocket authentication. | Default authentication, minted secrets, Origin or Host defence, revocation, log hygiene. |
| code-server (password, hash cookie) | Minted secret, loopback default, attempt limiting, Origin check on upgrade. | Per-browser sessions, expiry, rebinding defence; proof that the user is the OS user beyond reading a config file once. |
| VS Code `serve-web` (URL token, cookie) | Minted secret in a `0600` file, proof of OS identity by reading that file, URL-to-cookie exchange, `Sec-Fetch-Site` check, framing policy. | Revocation, short lifetime, `HttpOnly`, rebinding defence, a way to get the URL onto a phone safely. |
| VS Code tunnels (account, relay) | Strong identity, scoped expiring tokens, reachability from anywhere. | Independence from a third party; a pipe that is not trusted for browsers. Out of scope per the map. |
| Jupyter Server (token, cookie, Host/Origin/XSRF) | The fullest loopback defence set and the redirect-file delivery trick. | Rebinding defence off loopback, revocation, a clean record on untrusted content. |
| sshx (fragment key, no cookie) | A credential that never appears in a request line; no ambient credential, so no CSRF or cross-site WebSocket hijacking; relay cannot read the stream. | Revocation, per-browser identity, integrity of the stream, any defence against the party that serves the script. |
| Cockpit (PAM login, server-side session) | Server-side per-browser sessions, strict cookie, exact Origin default, CSRF token, hardened headers, idle timeout. | A credential minted by acting as the OS user; rebinding defence; a small pre-authentication surface. |
