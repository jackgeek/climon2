# Native scrollback restoration: evidence, not a UX decision

Research date: 2026-10-28. Scope: [Native scrollback restoration without clearing unrelated terminal history](https://github.com/jackgeek/climon2/issues/51), informing the still-open [Scrollback: retention, navigation, and attachment experience](https://github.com/jackgeek/climon2/issues/49) under [Wayfinder: session continuity, attachment, and scrollback release](https://github.com/jackgeek/climon2/issues/40).

## Bottom line

**Appending a sanitized rendering of daemon normal-screen history is the common candidate; selectively replacing an earlier session-owned copy is not an established portable capability.** Native scrolling, selection and copy remain native after append, with ordinary application input. This is not a custom history mode. Replaying a full retained snapshot can duplicate output on reattach/control regain and consume the host's independently bounded history. “Do not issue a destructive clear” is feasible; “no unrelated history can ever be lost while adding arbitrary history” is not a guarantee a client can make against a finite host buffer. [Apple limits][apple-window], [iTerm2 limits][iterm-settings], and [VS Code limits][vscode-basics] belong to the host, not the daemon.

No engine, replay policy, default change or UX is selected here. Accepted context remains daemon-owned normal-screen history (not a byte transcript or alternate-screen recording), normal/history width reflow, proposed 10,000 rows (0 disables), separate 32 MiB history default configurable up to 256 MiB; clients keep no emulator. No proposal here changes version matching, frozen hello/metadata, control ordering, placeholders, detach or session lifetime.

### Clears, marks and host-owned restoration are not selective import

- `CSI 3 J` means erase saved lines, **not** erase a session-owned suffix. Packaged xterm explicitly trims **all** off-viewport lines; `CSI 2 J` erases the visible display (with an option that can first scroll it), not an arbitrary historical range. Cursor addressing/insert/delete within the display cannot address arbitrary negative history rows. “Selective erase” in DEC terminology concerns protected cells, not daemon session ownership. Neither ED3 nor reset-and-replay is a preserving replacement algorithm. [Reference][ctlseq], [actual xterm ED implementation][xterm-erase]
- iTerm2 documents `OSC 1337;ClearScrollback`, routed to `terminalClearBuffer` in stable [dispatch source][iterm-dispatch]. `SetMark` records a navigation position. Apple documents user marks and clearing the most recent command while preserving others. These are **counterexamples to claiming all native partial clearing is impossible**, but not evidence of a portable, session-addressable replacement operation. [iTerm codes][iterm-escapes], [Apple marks][apple-marks]
- iTerm2 internally implements range replacement and suffix removal, and tmux-specific `setHistory:` **clears its target buffer** before importing history. VS Code has its own persistent reconnection/revive and scrollback restore setting. These prove hosts can implement restoration, not that an ordinary climon2 PTY client can replace just its history in an existing shared terminal. A dedicated host integration would be a different capability/installation decision, and cannot be inferred portable. [iTerm replacement][iterm-replace], [tmux import][iterm-tmux], [VS Code persistence][vscode-advanced]

## Attachment, control regain and preservation constraints

1. **Append/re-render, not replay original bytes.** The daemon can render retained normal cells in order as ordinary output, scroll them into native history, then draw the coherent normal viewport and restore live modes. Existing *visible* outer content must be moved out of the repaint area before clearing/overwriting the viewport; preserving only offscreen history is insufficient. Work in a known normal buffer with a full-height scroll region; partial regions do not necessarily append history. Exact bootstrap bytes, blank-row overhead, boundary wrapping and final cursor position need the native checks below. [xterm scroll][xterm-scroll], [iTerm preferences][iterm-settings]
2. **If the session is currently alternate-screen:** seed normal history and reconstruct the underlying normal screen, then enter/draw the current alternate screen. Do not append the alternate-screen snapshot as historical output. Availability of native browsing while alternate is active is host-dependent; native mouse reporting/alternate-scroll settings can route wheel/selection gestures to the application. This is an existing requirement tension, not permission to invent a browsing mode or disable application input. [iTerm settings][iterm-settings], [xterm buffers][xterm-bufferset], [VS Code mouse behavior][vscode-basics]
3. **Full retained history on each attachment/control period** can reproduce the same rows repeatedly. Neither an attachment ID nor a stable outer TTY name proves what survives a host clear, recycle, resize, restart, or unrelated intervening output. Non-controlling clients receive no hidden session output, so regain needs an ordered catch-up/restore boundary; simply resuming the last output frame misses history.
4. **Incremental seeding** could reduce repeats using daemon sequence/epoch watermarks (no client emulator needed), but only if a human contract chooses what “already delivered” means and where terminal identity/watermarks survive. A delivered frame is not proof it remains in native history. If the missed interval exceeded daemon retention, an explicit daemon-history gap can be rendered, but that says nothing about older host copies. Arbitrary application cursor edits mean “new rows” must be defined over finalized history rather than treated as a raw-output offset. This is design reasoning, not an existing host API.
5. **No universal exact de-duplication proof from output alone:** two outer terminals may have identical dimensions/cursor/query replies while only one retains the earlier copy. A client with no read/ownership oracle cannot distinguish these states to both restore missing history and suppress every duplicate. This is a limitation of that observation model, **not** a proof that host integrations or future APIs cannot solve it. Text matching via scripting is still not provenance: unrelated commands can print identical text; row coordinates shift with reflow/eviction.
6. **Capacity is separate from destructive clearing.** Appending can naturally evict unrelated oldest rows. Daemon 10k-row/byte limits cannot reserve host capacity (VS Code defaults to only 1,000 scrollback lines), remove old native copies, or bound them after daemon exit. Absolute preservation of arbitrary old host content plus arbitrary new history in a smaller finite buffer is a capacity contradiction; weaker “no explicit clear” wording is a decision, not a trick to promise both. [Host limits][vscode-basics], [scroll eviction][xterm-scroll]
7. **Source-of-truth reflow is not host reflow identity.** Preserve logical soft-wrap versus hard-newline boundaries when serializing; emitting CRLF after every physical daemon row makes those rows hard breaks, so later native resize cannot reliably rejoin them. Double-width/combining characters, delayed wrap at the right margin, trailing blanks and differing Unicode-width settings need explicit fixtures. Host reflow can change which rows remain without any new daemon output. Exact native indices and matching cutoffs cannot be promised. [xterm reflow][xterm-reflow], [iTerm width settings][iterm-text], [VS Code Unicode settings][vscode-advanced]

## Safe seeding and native anchoring

Seed from **parsed daemon cell/history state**, not an original transcript or an unreviewed full-machine serializer. Emit validated printable text plus a narrowly allowlisted, constructed rendition/wrapping sequence set. Reject/encode embedded ESC, C0/C1 controls and malformed/control-bearing cell content; select line movement deliberately rather than copying tabs/backspaces. Exclude BEL, ENQ, DSR/DA/color queries, OSC clipboard/title/notification/file transfers, arbitrary OSC/DCS/APC and history-clearing/reset controls. Queries can emit replies; bells/clipboard codes have external effects. Historical query answers must not flow to the running application or compete with the daemon's responder. Live-mode reconstruction is a separate, ordered operation; “strip every ESC” also destroys legitimate rendition and is not a complete serializer. [xterm query/BEL handlers][xterm-effects], [iTerm effectful codes][iterm-escapes]

This prevents **replaying encoded terminal side effects**, not all possible host reactions: VS Code configurable auto-replies can react even to text, and host notification/profile settings can change behavior. No claim of side-effect-free replay under arbitrary host customization is justified. [VS Code auto-replies][vscode-advanced], [iTerm alerts][iterm-settings]

**Live output matters too:** forwarding an application's ED3, reset or proprietary clear can still erase unrelated native history after a perfectly safe seed. Whether preservation applies only to restoration or also requires daemon-mediated filtering/rendering of live clears remains a human fidelity/preservation decision. Do not silently solve it by clearing or breaking the application.

No inspected common output protocol queries/sets the native user's scroll anchor or reports exactly which host copies were evicted. iTerm2 Python and xterm *host-side* viewport/overflow APIs are exceptions, not evidence that the CLI has them. Cursor save/restore is not viewport save/restore; synchronized redraw is not a scrollback transaction. A printed “daemon history truncated” boundary is possible, but remains ordinary host-retained text; native truncation icons, scroll position and retention cannot be promised or universally observed from the PTY. [iTerm line information][iterm-session], [xterm viewport API][xterm-api], [host scrolling][xterm-scroll]

## Feasible options and decisions left with the user

| Option (not selected) | What it buys | What still cannot be promised |
|---|---|---|
| Append complete sanitized retained history on restore | Self-contained catch-up in a fresh terminal; ordinary native UX; no destructive clear needed | No duplicates on reattach/regain; preservation from host-capacity eviction; full retained-history visibility under smaller host limits |
| Append only a daemon-tracked delivered-history suffix; fall back by an explicit rule | Fewer duplicates when the same outer terminal really retains earlier rows | Recovery of user-cleared/evicted copies, stable TTY identity, exact once-only display; schema/state lifetime/gap rule remain open |
| Explicit user-requested replay or fresh/dedicated outer terminal | User chooses duplication/isolation; dedicated buffer reduces interference with unrelated content | Automatic existing-terminal de-duplication; same retention/alternate-screen/width caveats; do not launch a terminal without a separate decision |
| Optional host-specific integration | iTerm history/viewport inspection or host-controlled restoration can improve evidence | Supported selective replacement across all targets; new permissions/install/integration work; not an accepted first-release dependency |

Human decisions already belong to [Scrollback: retention, navigation, and attachment experience](https://github.com/jackgeek/climon2/issues/49), [Daemon virtual terminal: engine, ownership, and failure boundaries](https://github.com/jackgeek/climon2/issues/43), [Multiple clients: control, hand-back, and terminal sizing](https://github.com/jackgeek/climon2/issues/47), [Protocol 2: atomic restore, live output, and slow clients](https://github.com/jackgeek/climon2/issues/48), and [Session continuity: automated harness and release acceptance](https://github.com/jackgeek/climon2/issues/45):

- Full replay versus delivered-suffix semantics, repeated-attach/regain duplicates and gap labeling; terminal identity/watermark lifecycle.
- “Never explicitly clear unrelated history” versus the unsatisfiable stronger finite-capacity guarantee; restoration-only versus live application clears.
- Native-history accessibility during alternate screen/mouse reporting; per-host qualification/fidelity limitations and host settings.
- Degree of soft-wrap/style fidelity; whether optional integrations or explicit replay controls are acceptable. Existing config startup/schema questions remain unfinished.

**Newly sharpened, not a new ticket:** capacity eviction versus explicit erasure, and live application clears versus restore-only preservation. Both fit the existing scrollback/fidelity children; no uncovered map-level question or ADR conflict was identified.

## Honest acceptance oracles and smallest remaining check

**Performed:** primary documentation/source inspection; noninteractive plist/XML reading; exact packaged xterm dependency resolution via public lockfile/package metadata. Automated checks passed: 27 used/resolved citation definitions; 15 GitHub URLs across 11 primary files fetched with valid line ranges; 18 source/dictionary/dependency assertions. **Not performed:** running native Terminal.app/iTerm2/VS Code, sending terminal controls, querying a user's buffers, clipboard checks, browser/GUI automation, or product implementation. Source checks are not native behavior tests.

Automated acceptance should separate these oracles:

1. **Daemon/serializer tests:** known normal cells, hard/soft wraps, wide/combining text and bounded-history eviction; independently parse emitted seed bytes and assert no forbidden controls, query/clipboard/bell/clear events or synthetic application replies. Check normal and inactive-normal/active-alternate restoration plus snapshot/live ordering at a single sequence boundary. Assert non-controllers get no hidden data.
2. **Protocol/regain tests:** attach → output → accepted detach → output → attach; lose/regain control with intervening output, resize and overflow. Assert the *chosen* replay/suffix/gap semantics and no missing ordered live frames. A generic emulator can test these contracts, **not prove any native host's history or anchoring**.
3. **Actual-host oracle, still unproven:** in a newly created disposable terminal *only with future explicit permission*, write unique unrelated sentinel rows, then use an isolated fixture to seed numbered normal rows, redraw, toggle alternate screen, resize 80→40→120 columns, reattach and regain. Use a host read API where available (AppleScript history; iTerm transaction/content/overflow/viewport); use isolated VS Code host instrumentation or UI selection/copy for that target, not shell-execution stream capture as a substitute for buffer state. Assert sentinels still exist when capacity suffices, count duplicates according to the agreed rule, compare copied logical text, verify mode/input behavior and scroll position while scrolled up. Repeat with host capacity below seed length: expected oldest-row eviction must not be misreported as a preserving success.
4. **Minimal manual residue:** on each named installed host/build/profile, scroll and select/copy across one soft-wrap boundary while output arrives and while alternate-screen/mouse mode is active; confirm viewport behavior and any native truncation affordance. Use a benign test clipboard sentinel and disabled/recorded alerts only in that isolated test environment. Automating an equivalent host UI check is valid; substituting another terminal engine is not.

No interactive check above was executed. Terminal.app normal seeding/reflow and all native selection/anchor behavior remain the smallest targeted prototype/qualification work, not blockers to finishing this evidence report.
